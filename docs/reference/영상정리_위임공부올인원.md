# 영상 정리 — 「작은 기업 대표를 위한 위임 공부 올인원」 (공여사들)

- 원본: https://youtu.be/jYNvdjh0yTo (2026-09-24 업로드, 6시간 18분, 구조수업 1~4기 16편 합본)
- 정리 방식: 전체 자막(약 9,900줄)을 끝까지 읽고 챕터별로 정리. 화면 설명은 발표자가 화면을 보며 말한 내용 기준.
- 표기: 📺 = 영상 속 실제 화면/시연 예시, 💡 = 강의에 바로 쓸 한 줄

## 0. 한 문장 요약

> **"대표가 잊어도 일이 사라지지 않는 구조"를 먼저 만든 사람이 위임에 성공한다.**
> 그 구조 = ① 일을 담는 단위(타스크) ② 일이 담길 정해진 자리(SSOT) ③ 대표 머릿속 기준을 꺼낸 문서(온보딩·SOP·히스토리).
> AI도 똑같다. **AI는 잘 쓰는 회사가 아니라 잘 쌓아 둔 회사에서 작동한다.**

## 2. 덩어리별 핵심 정리

### A. 문제 진단 — "사람이 아니라 구조의 문제"

**대표 100명에게 던진 4가지 질문 (90%가 같은 답)**

| 질문 | 대부분의 답 |
|---|---|
| 매뉴얼이 있나요? | 없습니다 |
| 업무 소통은 뭘로? | 카톡 |
| 히스토리는 어디에? | 카톡 |
| 신입 교육은 누가, 얼마나? | 대표가, 3개월 |

- 대표 머릿속 기준이 직원에게는 **존재하지 않는** 상태. 좋은 사람을 뽑아도 결과는 같다.
- 직원 3명 넘었는데 이 상태면 → 사람을 더 뽑지 말고 구조부터.
- **시스템 없이 일하는 3가지 증상**: ① 정보 위치를 몰라 사람을 붙잡고 묻는다 ② 시작·마감·일정을 가늠할 수 없다 ③ **몇 점을 맞아야 잘한 건지 기준이 없다**
- 대기업과 주먹구구 회사의 가장 큰 차이 = **"일이 사람에 달려 있느냐"**
  - 통신공사 예: 요청 들어오면 "D+3 내 완료"가 기준. 담당자가 연차면 옆 사람이 처리. 마감 지나면 빨간불(여기까지가 시스템의 역할), 그래도 안 하면 KPI.
- 실패담: 처음엔 대기업식 풀 시스템(자재코드·재고·수금…)을 지어줬다 → 무거워서 실패. **작은 회사는 가볍고 유연한 최소 시스템만 살아남는다.**
- 왜 다들 사람 탓을 하나? → **사람 탓이 제일 싸서.** 대기업은 사고가 나면 시스템 대신 **SOP를 고친다.** SOP는 직원의 우산(보호막).

💡 "시스템은 여유가 생기면 만드는 게 아니라, 여유를 만들기 위해 지금 만든다. 오늘이 제일 쉽다."

### B. 최소 시스템 3종 세트 — 온보딩 · SOP · 히스토리

| 구성 | 정의 | 반드시 들어갈 것 | 왜 |
|---|---|---|---|
| **온보딩** | 신입이 첫날 보는 한 화면 | 무엇을 파는지·고객·제공 가치 / 누가 무슨 일 / 어디에 뭐가 / 규정·근태·연차 → **단계별 배치**(1단계에 볼 것, 2단계에 볼 것) | 채용마다 반복, 거의 안 바뀜. 지시보다 **이유·배경·목적**을 줄 때 사람이 움직임 |
| **SOP** | 처음 할 때 적고 반복될 때 그대로 하는 문서 | ① **목적·배경·근거·사유** ② 절차 ③ **완료 기준** ④ 최소 품질 기준 | SOP는 잘하게 하는 도구가 아니라 **결과물의 최소 기준을 맞추는 장치** |
| **히스토리** | 의사결정의 이유와 시점 기록 | "**이런 이유로, 이 시점에, 이렇게 결정했고, 그래서 이렇게 세팅했다**" 2~3줄. 실패 이력·제안자 포함 | 새 담당자가 올 때마다 같은 논쟁 반복 방지 |

- SOP 트리거 규칙: **1회 이상 반복될 것 같은 일은 할 때 바로 SOP로 적는다.**
- SOP에 목적이 있어야 하는 이유(📺 메타 광고 예): 버튼 이름이 "완료"→"제출"로 바뀌어도 목적(광고 송출)을 알면 스스로 판단한다.
- 완료 기준 불일치 예: 광고 소재 제작 — 대표는 "메타에 게시"를 완료로, 직원은 "디자인 끝"을 완료로 생각.
- 히스토리의 그릇 = 프로젝트 관리 · 공유 일정 · 회의록.
- 모든 문서의 첫 꼭지는 **목적·명분·배경·근거·사유** = AI 시대의 "맥락".

**DX/AX 순서 (대기업 DX 프로젝트 경험)**
1. **일 목록 정리** — 우리가 하는 일이 무엇인가
2. 일을 **순서대로 배치**, 각 일의 목적·순서를 정리해 SOP 작성
3. SOP를 뜯어보며 구멍·비효율 발견
4. **덩어리 큰 비효율부터** 시스템화·자동화
→ 프로세스가 없는 자동화 논의는 시기상조.

**직원을 믿게 되는 3단계**: 셀프 체크리스트 → 틀릴 때마다 "왜·어떤 판단으로·결과" 기록 → 스스로 판단하는 구조

### C. AI 도입 — "AI는 잘 쌓아 둔 회사에서 작동한다"

- 흔한 장면 3개: 마케팅 글(톤·타깃·잘 먹힌 구조가 없어 30번 피드백) / 회의록 요약(왜·누가 반대했는지 빠짐) / 영업 답변(과거 대화·약속이 없어 사람이 다시 뒤짐) → **AI가 일을 줄인 게 아니라 일의 단계를 하나 늘렸다.**
- 핵심 명제: 걱정할 건 AI 성능이 아니라 **AI에게 회사 정보를 어떻게 넘기느냐.** "회사 맥락 없는 AI는 앙꼬 없는 찐빵."
- **툴은 바뀌어도 맥락은 바뀌면 안 된다** → 맥락을 개별 AI 툴 안에 가두지 말고 통합 공간(마크다운 기반)에 쌓는다.
- 먼저 AX할 업무 선정 기준: ① **측정 가능**(끝이 명확, 성공 기준 단순 — 블로그 1편 발행) ② **SOP로 쓸 수 있음** ③ **사람이 몇 달 성실히 쌓은 데이터가 있음**(CS 두 달 수작업 답변 → FAQ → 자동화). 판단 지점이 수백 개인 일(영상 편집)은 자동화 어려움.
  - 💡 "매뉴얼이나 설명서로 만들 수 있는 업무는 모두 AX가 가능하다."
- **사람 검수 원칙**: 내부용(회의록·발표자료·리서치)은 전부 자동화 OK / **밖으로 나가는 것**(고객 콘텐츠, 파트너 메일)은 반드시 사람이 한 번 검수. 기준 = 틀렸을 때 매출·평판에 영향이 큰가.
- AI 활용 성숙도: ① 챗봇 → ② GPTs·프로젝트·Gems(고정 맥락 재사용) → ③ Claude Code/Codex로 직접 개발 → (잘하는 팀) **데이터부터 모으고 그 위에 AI 빨대를 꽂는다.**
- **SSOT (Single Source of Truth, 단일 진실 공급원)**
  - SOP = "어떻게 일할까", SSOT = "**무엇을 보고** 일할까"
  - 💡 "원본이 여러 개면 원본이 없는 것과 같다." (카톡엔 돈가스, 회의록엔 김치찌개, 드라이브엔 옛 메뉴판)
  - 작은 회사 버전 SSOT = 정보별로 자리를 정하는 것: 고객→고객DB / 업무 담당자→업무DB / 상품→상품DB / CS 기준→CS 매뉴얼 / 일정→일정DB / 콘텐츠 일정→콘텐츠DB / **회의 결정→해당 DB에 최종 반영**
  - 대화는 어디서 해도 된다. 단, 결정은 회의록 → 실제 일하는 DB까지 반영되어야 원본이 된다.
- 📺 노션 AI 3단계: ① AI 자동 회의록(메모·받아쓰기·요약 탭, 액션아이템에 담당자+기한+리마인더) ② 회사 전용 AI(워크스페이스 기반 Q&A) ③ **스킬**(반복 AI 작업을 매크로처럼 저장, "스킬도 AI에게 짜게 하라")
- 📺 스킬 예: 광고 카피 스킬 — 베스트 리뷰·고객 고민·고객 실제 언어·시장조사·이전 소재 성과를 참조, "지어내지 말고 고객 언어에 있는 워딩만". 공통 페이지로 **금지어 리스트**(약 100개)·**상품 도메인 지식**을 두고 모든 스킬이 참조.

### D. 업무 관리·위임 — "타스크"가 모든 것의 출발점

**카톡·슬랙으로 일할 때의 3가지 문제**: ① 안 보인다(최근순, 결정이 안 남음) ② 찝찝하다(알림 의존, 놓치면 사람이 욕먹음) ③ 안 남는다(다음 업무에 도움 안 됨)

**직원을 뽑아도 느려지는 3가지 이유**: ① **업무 접수 착시**("확인했습니다" ≠ 맡았다) ② **스위칭 비용**(대표 머릿속 순서 = 일의 순서) ③ **누락 책임이 아무에게도 없음**

**업무 "접수"가 되는 3조건** ⭐
1. **누가** (담당자 — 1명)
2. **언제까지** (마감일)
3. **어디까지 하면 끝나는지** (완료 기준·범위)

> 타스크 = "마감 기한이 있고 담당자가 있는 하나의 확실한 실행 처리 단위"
> 이 셋이 없으면 **업무가 아니라 대화**다.

**타스크는 종합예술 — 3요소가 동시에 작동해야**: ① 업무를 지시할 공간 ② 푸시 알림(새 업무·마감일) ③ **완료될 때까지 양쪽 화면에서 사라지지 않음**. 하나라도 빠지면 대표나 일잘러가 그 역할을 대신하게 된다.

**업무의 3층 구분** ⭐
| 층 | 정의 | 예 |
|---|---|---|
| **타스크(업무요청)** | 담당자·마감이 있는 실행 단위 | 물티슈 채우기, 상품 재등록, API 권한 변경 요청 |
| **프로젝트** | 상하위가 있는 큰 덩어리, 수반 행동 수백 가지 | 신제품 출시, 정부지원사업, 출판, AX |
| **SOP(업무 절차)/스킬** | 두고두고 참고하는 절차 | 메타 광고 소재 일괄 업로드 SOP |
→ 크기가 다른 일을 같은 그릇에 담지 않는다. 프로젝트에 딸린 작은 일은 타스크로 보내되 **상위 프로젝트를 멘션**.

**운영성(O) vs 프로젝트성(P)** ⭐
- 운영성 = 본업이 되어 반복되는 일, 반복 매출이 만드는 반복 업무, 경영·회계·세무 같은 공통 업무
- 프로젝트성 = 처음 하는 일, 비고정, 대표도 답을 모르는 일
- 대표의 숙제: P를 반복 매출이 나는 형태로 바꾸고 → 반복되면 O로 고정 → 시스템화. 진짜 숙제는 **P단의 효율화(쪼개기)**.
- 💡 "일을 한 덩어리로 뭉쳐서 다 똑같은 일로 보면 답이 없다."

**대표 유형 4사분면** (축1: 일이 사람 머릿속 vs 밖에 / 축2: 대표 시간이 오늘 일 vs 다음 일)
- 목표 = **열어보면 알고 + 대표 시간은 다음 매출·고객·시장에**. 보고 트리거는 **이슈 발생**과 **대표 리소스 필요** 두 가지뿐.
- 💡 "일을 못 놓는 게 아니라 놓을 수 있는 조건이 없는 것. 보여야 맡길 수 있다."
- 💡 "모든 걸 다 보여주는 건 아무것도 안 보여주는 것과 같다." → 숲(전체) 먼저, 이슈만 깊게.

**위임의 정의**
- "일을 맡겼다면 대표가 기억을 잃어도 끝까지 진행돼야 하는 게 일이다."
- "대표가 묻지 않으면 멈추는 일이 있다면 아직 맡긴 게 아니다."
- 진단 질문: **"대표님이 묻지 않으면 멈추는 업무가 지금 몇 개입니까?"**
- 위임의 두 불안: **품질**(→ 온보딩·SOP·히스토리, 100점이 아니라 **누가 해도 80점**) / **완수**(→ 쪼개기 + 타스크 단위로 주고받기, 끝날 때까지 안 사라짐)
- 위임이 되는 일 = 대표가 여러 번 해봤고, **최소 기준이 러프하게라도 명확한 일**. 안 되는 일 = 대표도 안 해본 일("이렇게 하면 될 것 같은데") → 대표 머릿속 "애프터"와 직원의 애프터가 다름. 처음 하는 일은 **먼저 쪼개서** 맡긴다.

### E. 실제 화면과 원칙

**"넣을 자리"의 원칙**: 노션에 다 적었는데 못 찾는 이유 = 일이 생길 때마다 넣을 곳을 새로 정하기 때문. 💡 차키 비유 — 자리가 정해져 있으면 넣을 때도 0초, 찾을 때도 0초.
- 시스템을 만든 이유 두 가지: ① 일이 생기면 **어디로 들어갈지** 명확 ② 대표든 직원이든 **언제 어떤 화면을 볼지** 정해짐

**일을 어디로 보낼지 (라우팅 표)** ⭐
| 상황 | 보낼 곳 |
|---|---|
| 오늘·마감 안에 반드시 처리할 실행 단위, 사람 간 지시 | 업무 요청함 |
| 한 번뿐이지만 크고 복잡, 여러 사람·오래 걸림 | 프로젝트 관리 |
| 앞으로 또 할 것 같은 일, 다른 사람도 할 일 | SOP(업무 절차) |
| 대표가 매번 판단하지 않아도 되는 기준 | 정책·지침 |
| 같이 보면 공부가 되는 외부 자료 | 공유 자료실 |
| 결재·근태·초과근무·연차 | 운영 메뉴 |
| 뭔가 사달라는 요청 | 구매/결재 요청 |

**담당자 1명 원칙**: 두 명에게 시키면 둘 다 하지 말라는 뜻(물티슈 비유 — 둘 다 안 사오거나 둘 다 사온다).

**쉬운 시스템의 정의**: 선택지가 적고, 채울 칸이 적다. 칸이 20개면 다들 한두 개씩 비우고 → 빈칸이 쌓이면 정보 가치 상실 → 메뉴를 안 쓰게 된다. 7~80점짜리처럼 느껴지는 시스템이 오히려 정착한다.

**프로젝트 관리에 필요한 건 3가지뿐**: 각 **단계**가 무엇인지 / 단계별 **담당자** / **언제까지**. 간트·타임라인보다 **표**가 낫다. 시작일보다 마감일.

💡 "좋은 시스템은 쓰라고 강요하는 게 아니라 안 쓰면 손해인 구조여야 한다."
💡 "노션은 껍데기이고, 파는 본질은 그 껍데기에 묻힌 생각들이다."

## 3. 📺 화면 예시 모음 (시연된 구조)

### 3-1. 업무 요청함 (가장 중요한 메뉴)
- 구역: **내가 요청한 업무 / 내가 받은 업무 / 전체 탭 / 보관함**, 기본 필터는 본인 관련만
- 입력: **제목·세부 내용 / 담당자(1명) / 마감일** → [요청 보내기]
- 상태 흐름: **요청 → (확인 댓글) → 회신 완료 → 완료** / 분기: **보류**(→보관함), 삭제
- 동작: 받는 사람에게 푸시 알림 → 마감일 아침 자동 알림 → 마감 지나면 빨간색 → 처리 후 [회신하기] → 요청자 화면에 "회신 완료"로 도착 → 요청자가 확인 후 **완료 처리** → 보관함
- **완료 처리 전에는 절대 화면에서 사라지지 않는다** ("가짜 업무함이 아닌 구조")
- 업무 1건 = 페이지 1개: 댓글·캡처·링크·기획 과정·의사결정이 모두 그 안에 쌓임 → 관리 + 지식 축적이 동시에
- 9가지 사용 상황: 오늘 할 일 / 주말에 생각난 일(마감 넉넉히 또는 수신자 없이 "내 업무"로 적어 뒀다가 월요일에 일괄 배정) / 부재 중 / 직원끼리 / **직원→대표("보고를 가장한 업무 지시")** / 누락이 드러날 때(재합의) / 일이 쌓였을 때(보류·삭제) / 혼자 하는 일 / 프로젝트 하위 일(상위 프로젝트 멘션)
- 채널 기준: 바로 안 끝나는 일·놓치면 안 되는 일·자산으로 남길 일 → 업무 요청 / 가벼운 대화 → 메신저 / 초긴급(몇 시간 안) → 말·전화 / 급한데 기록도 필요 → 업무요청 올리고 메신저로 "올렸어요"

### 3-2. 프로젝트 관리
- 진행 중 프로젝트를 **한 화면의 표**로. 상태: 미완료 · 진행 중 · 완료 · **이슈** · 보류
- 대표는 **이슈로 표기된 것만** 깊게 들어간다. 끝난 프로젝트 → **프로젝트 보관함**(시즌 프로모션·신제품 런칭 등 반복 프로젝트 재참조, 인수인계 자료)

### 3-3. SOP 영역 (업무 파트별: 경영지원, 콘텐츠 …) — 4분류
1. 단순 매뉴얼(클릭 조작법) 2. **업무 절차(SOP)** 3. **정책·지침** 4. **스킬**(AI용)
- 작성법: 1·2·3·4·5 단계 + 단계마다 캡처 + 빨간 박스·파란/빨간 글씨 강조 + "복사하세요→붙여넣으세요→확인하세요" 식 행동 지시. **일하면서 캡처, 따로 날 잡지 않음.**

### 3-4. 공통 일정·회의·회의록 (하나로 통합)
- 일정 DB를 주간·월간·간트 뷰로. 유형(개인 일정/내부 회의), 참석자
- 회의는 반드시 일정으로 등록 → 그 안에서 AI 회의록(메모 / 받아쓰기 / 요약) → 액션 아이템에 **담당자 멘션 + 기한 + 리마인더**

### 3-5. 홈 화면과 운영 메뉴
- 홈: 공지사항(읽음 확인) / 공유 일정(오늘 일정·연차) / 주간 업무 보고(월요일) / KPI(매월 첫째 주 자동 생성)
- 운영 메뉴: 결재·구매 요청(대표는 "결재 대기함"만) / 근태·초과근무·연차 / **정기 결제 관리**(AI 구독 등 고정 지출) / **공용 계정 관리**
- 기타: 상품 기획(상품 정보·리뷰), 광고 소재 기획 DB, 마케팅 로그(활동 기록 + 사후 평가), 공유 자료실, 금지어 리스트
- 전체: **표준 30종 메뉴**, 2년간 추가·삭제 없이 사용. 안 쓰는 메뉴는 삭제 말고 숨김.

### 3-6. 대표의 하루 루틴
매일 아침 홈(공지·일정) → 내 업무함(시킬 일·시킨 일·회신 온 일 검토, 완료 처리) → 수신함 / 월요일 주간 보고 / 월초 KPI / 프로젝트는 필요할 때 / 결재 대기함
💡 "사람한테 물을 바에는 AI에게 먼저 묻는다." / "저는 회사를 뒤지지 않습니다. 회사가 이 안에 다 들어 있을 뿐."

**보고 체계의 진화**: 업무 요청으로 일일 추궁 줄이기 → 주간 업무 보고 → 월간 KPI

**목표 캐스케이드(대기업식)**: 사업계획 → 연간 KPI → 실행 과제·액션 아이템(일정) → 월 단위 관리 → 주간 업무 → 사전·중간·최종 보고

## 4. 1인 기업·AI 에이전트에 대한 영상의 견해 (중요)

- 1인 기업의 약점: 내가 아프면 매출이 멈춘다.
- AI 에이전트로 확장은 가능하지만, 계속 지켜보며 시키면 "삶을 포기하는 것"과 같다 → **에이전트가 대표 없이 굴러가려면 사람 팀과 똑같은 구조(타스크·SSOT·SOP)가 필요.**
- **개인 AI 기억 vs 팀 지식 분리**: 개인 AI는 내 습성을 기억해서 "저번엔 A, 이번엔 B"가 된다. 회사 기준·도메인 지식은 AI 기억이 아니라 **공용 저장소(SSOT)**에 둬야 한다.
- AI는 5~10인 조직의 체급을 키우는 도구라는 관점.

## 5. 영상에서 "업(業)"은 어떻게 다뤄졌나 — 정직한 정리

영상은 **"업(業)" 자체를 정의하는 대목이 없다.** 문맥상 "업 = 회사가 하는 사업과 그 도메인"이라는 뜻으로만 쓰인다("내 업의 도메인 지식", "업의 변화에 맞춰 시스템을 복제·수정").

대신 **업무(일)의 정의와 분해**는 매우 구체적이다:
- 업무 = 담당자 + 마감 + 완료 기준이 있는 것 (없으면 대화)
- 일의 크기 3층: 타스크 / 프로젝트 / SOP
- 일의 성격 2분류: 운영성(O) / 프로젝트성(P)
- 비즈니스 모델 = "회사가 반복적으로 매출과 수익을 내는 구조"
- 업무 구조화 순서: 일 목록 → 순서 배치 → SOP → 비효율 발견 → 시스템화
- 잘한 일 = 사전에 합의된 완료 기준과 최소 품질을 충족한 것

→ 강의에서 "업의 정의"를 다루려면, 위 재료를 **업 → 사업모델 → 업무영역 → 운영/프로젝트 → 타스크**로 이어 붙이는 틀이 필요하다. 그 틀은 `02_강의안_업과업무의정의.md`에 별도로 설계했다. 영상에서 온 내용과 새로 설계한 부분을 구분해 표시했다.
